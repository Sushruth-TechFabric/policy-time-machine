# Fraud truth is conditional on existing behaviour and held outside the medallion schemas

Every existing source table must stay byte-identical for a given seed and anchor — the fifteen Genie contracts and ADR-0014's calibration checks are asserted against them — so a fraud label cannot be decided first and behaviour generated to match it. The direction is reversed: `ptm_eval.claim_fraud_truth` (`claim_id`, `is_fraud`, `population`) is drawn, one row per claim, from a new `truth` RNG stream after every other table is final, conditional on the behaviour that table already contains. No existing row moves.

Measured on the generated book: 1,285 claims — 150 S (a noteworthy scenario planted the claim), 135 C (the claim sits on a control policy), 1,000 background. Behaviour has no variance inside S — one flagged claim in 150 — so the S rate is flat at 40% (60 of 150) rather than tilted by any behaviour flag, and inside that rule-matched group the claim note is the only evidence that separates the sixty fraud claims from the ninety benign ones. C is exact zero across all 135 claims: a control claim is never fraud. The background rate is 3% (30 of 1,000), tilted by three declared odds ratios applied to behaviour that already exists in the emitted tables — early tenure 3.0, recent reinstatement 2.5, new vehicle 1.5 — of which only early tenure produces a measurable effect at this book size; the other two shape the allocation by a claim or two and are kept because they are declared, cheap, and grow with the book.

Allocation is exact, not sampled. Within a population the fraud count is `round(rate × claims)`; for the background, claims are grouped into strata by flag pattern, a logistic intercept is solved so the expected total equals the declared count, each stratum's share is fixed by largest-remainder rounding, and the RNG stream only chooses which claims inside a stratum carry the label. This is why the checks in spec 01 §9 are equalities rather than tolerances for rates, strata and tell counts, and it is the same calibrated-not-sampled approach the generator already uses for severity bands.

The table lives in `ptm_eval`, a schema of its own outside the medallion layout ADR-0016 describes. Isolation here is not a grant: the regeneration job's run-as identity is the one that creates and owns `ptm_eval` — its schema, volume and `claim_fraud_truth` table (`generate_task.py`'s DDL, `load_source_tables.py`'s CTAS) — and that same identity later runs `route_claims`, `build_briefs` and the agent harness in the same job run, so a grant cannot keep it from a schema it owns. What keeps the agent off the truth is construction, not permission: the harness's Unity Catalog tools are fixed, parameterised SQL over named gold tables (`app/backend/review/tools.py`); the one tool the model drives, `ScratchSql`, runs only against the Lakebase Working Branch, never against Unity Catalog; Genie is limited to its six attached gold tables; and the application service principal and the Genie space are granted nothing on `ptm_eval`. A schema of its own still earns its place: a later bronze or gold grant can never expose the truth by accident, since there is no such grant to widen, and the repo test can forbid the name outright.

Three alternatives were rejected. Separate "F" scenarios in the style of S1–S6 would make fraud rule-findable by construction — the exact thing the evaluation bench exists to show is not already true of the rule set. Model-written notes would break the byte-stability and determinism obligations spec 01 §10 already commits to, and would make the generator's own tests depend on a model call. Growing the book for more measurable signal was rejected because the byte-identity constraint means this book is exactly what the fifteen Genie contracts and the existing calibration checks were built against; changing its size reopens all of that for a benefit spec 01 §9 already gets a different way — the reference scorer and the rules-only proxy are measured on the same book and read from the validation report, not chased with more data.

## Consequences

- Byte identity is asserted by the generator test suite (`generator/tests/test_byte_identity.py`) against golden hashes recorded before this change. Every other check in spec 01 §9 — declared rates, tilts, tells, the separability band, the rules-only proxy, leakage — runs inside the existing `validate_task` and fails a bad regeneration the same way the pre-existing checks do.
- The truth-isolation repo test (`generator/tests/test_truth_isolation.py`) fails the build if `claim_fraud_truth`, `ptm_eval` or `is_fraud` appears under `app/`, `pipeline/`, or in the Genie space definition; those names are permitted only under `generator/`, `workflow/`, `ci/` and `docs/`.
- `claim_context` is a gold table but stays out of the Genie space in this sub-project. Attaching it later is a decision that comes with a full contract re-run, not an incidental grant.
- The Workflow's load step writes `claim_fraud_truth` to `ptm_eval`; the declarative pipeline never reads it.
- The job's run-as identity owns `ptm_eval` and can necessarily read it; no other identity is granted anything on it. The agent that identity runs is kept off the truth by construction — fixed, parameterised gold-table SQL, a Working-Branch-only scratch tool, and a six-table Genie space — not by a grant it lacks.
- No agent that runs under the job's run-as identity may be given free-form Unity Catalog SQL; if the investigator agent (sub-project D) needs it, its tasks run as a principal with no access to `ptm_eval`.
