# Materiality is a fixed category set, not a lineage or magnitude test

A change is material if it falls in one of five decision categories: coverage, deductible, vehicle, address, status. (Originally six — `property` was removed by ADR-0005, which scoped the product to personal auto.) Premium and agent changes appear on timelines but are never material. Renewal is a timeline event, not a change. There is no magnitude threshold and no change-lineage tracking.

We chose this because the alternatives cost more than they return for a competition MVP. Tracking `change_origin`/`parent_change_id` is faithful to how policy administration actually works, but it moves correctness into the synthetic data generator, where a causation bug corrupts materiality silently. Promoting Endorsement to a grain reads beautifully on a timeline but forces every count column to re-decide which grain it means, reopening decisions settled in ADR-0002. Counting everything — including premium — would make "three material changes in 30 days" routinely mean one decision plus its echoes, which breaks the product's central claim.

## Consequences

- **`endorsement_id` is carried as a column on both event tables, not as a grain.** The generator knows which changes it committed together, so the information is free. It lets the timeline group co-committed changes into one card, gives `COUNT(DISTINCT endorsement_id)` as a fallback counting definition if field-level counts ever look wrong, and answers "wasn't that one customer interaction?" with data.
- **Status stays material, and the generator carries the burden.** Lapse/reinstate sequences are emitted only as deliberate scenarios, present in both the noteworthy and control populations. Renewal-driven status recalculations are never emitted as change events — that would be the premium-echo problem re-entering through a side door.
- **"Any change is material" for coverage and deductible only holds because the generator controls magnitudes.** Real data would force thresholds here. Stated so nobody mistakes the omission for a considered position on real-world data.
- **A standalone premium change — a rate revision with no coverage change — is invisible to material counts.** If the demo needs it, it becomes a named Noteworthy Pattern rather than a materiality exception.
- **Typed value columns are required.** `old_value_num`/`new_value_num` alongside the text pair, plus a materialized `change_direction` and `change_pct`, so "coverage increased" never depends on Genie casting strings. `change_pct` is NULL for categorical categories and when the old value is zero or null — never a sentinel, never infinity. `change_direction` is `'switch'` for every categorical change and never NULL, so "all increases" excludes categoricals by value rather than by NULL handling.
